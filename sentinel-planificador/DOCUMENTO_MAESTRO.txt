## 2. Visión y alcance vigente

SENTINEL es una herramienta personal de automatización y evaluación del auditor como Project Manager: planificar, registrar oportunamente, controlar la operación, comunicarse y evaluar mejoras. No se presenta como sistema corporativo aprobado. No registrar datos sensibles, números individuales de contenedores ni archivos adjuntos.

La nueva especificación sustituye el concepto, diseño y flujos de la APK inicial FARO. No basta renombrar la APK anterior. Este planificador de tareas tampoco es la aplicación operativa.

Arquitectura funcional vigente: dos interfaces Access distintas, Auditores y Supervisión, con datos principales compartidos en SharePoint Lists. Supervisión incluye las funciones de Auditores más supervisión. Todos pueden crear servicios/tickets. La evaluación individual y cierre/revisión son de acceso exclusivo del propietario; ese acceso no se extiende automáticamente a todos los usuarios de Supervisión.

La decisión antigua de backend Access exclusivamente local y entrega de tres ACCDB queda sustituida por SharePoint Lists como base principal. Se prevén dos frontends ACCDB; el empaquetado concreto del código/backend debe definirse en arquitectura, sin volver a inventar una tercera base Access local de datos. Sin instalador. No se han creado ni validado las Lists para esta reestructuración.

No integrar IA. El propietario copiará la evaluación completa, incluyendo sus notas, y la llevará voluntariamente a una IA externa para preparar su discurso de retroalimentación. Tampoco hay sincronización automática del planificador con Drive, GitHub u otros chats.

## 3. Decisiones funcionales y correcciones obligatorias

Arquitectura vigente: Dos UI Access (Auditores y Supervisión), con datos principales en SharePoint Lists. La decisión de usar solo Access local queda sustituida.

Reestructuración: Lo acordado para SENTINEL sustituye la concepción y flujos de la APK inicial FARO. Esta nueva versión todavía no está implementada.

Diseño fijo: Conservar la primera distribución de SCHEDULE: cinco tarjetas originales, filtros y filas de dos líneas. Solo cambios expresamente solicitados. Encabezado SENTINEL | SCHEDULE; nombre de usuario sin rol, avatar ni etiqueta Datos locales. Isotipo portuario, nunca escudo; alternativa definitiva pendiente.

Servicios: Todos pueden crear tickets con ID automático único. Catálogo de buques; falta decidir quién puede editarlo.

Acceso: ENTRAR abre preliminares antes del inicio. CONTINUAR para responsable vigente. VISUALIZAR para otros, sin modificaciones. Responsable y último editor se guardan por separado.

Preliminares: REGISTRAR CAMBIOS guarda sin iniciar. INICIAR OPERACIONES valida, guarda, registra inicio/responsable y abre trabajo.

Pausa y mando: Pase de mando mediante botón de pausa: otro auditor puede continuar y queda registro. Solo propietario y responsable pueden habilitar el pase. No pantalla adicional de entrega/recepción.

Pantallas operativas: Hoja de vida, estimado, hourly, arrival, departure, shifting y CRM. Recursos en estimado/hourly; demoras junto a la hora reportada. No pantallas separadas de plan, recursos ni hitos.

Coletillas: Los llamados hitos son títulos/coletillas superiores de la hoja de vida. Nombres en inglés según referencia del usuario; falta confirmar texto exacto.

Tareas e historial: Cada selección o campo por llenar es una tarea. Panel de realizadas con check verde. Registrar cambios por campo, usuario y fecha/hora para evaluar oportunidad antes/durante/después de operaciones. Reglas exactas del check por definir.

Evaluación privada: Evaluación PM 0–100 visible solo al propietario, notas por renglón y cierre/revisión privados. Ponderaciones por aprobar. Distinguir errores de cálculo de cambios operativos. Sin IA integrada; copiar evaluación completa para IA externa.

CRM: Registrar conversaciones con puerto y planners, acuerdos, responsables, plazos y seguimiento. Campos y reglas finales pendientes.

Sin adjuntos: No adjuntos ni números de contenedores ni información sensible. Solo reportes definidos para generar/imprimir. La evaluación de personal igualmente requiere privacidad real.

Respaldo: Un botón HACER RESPALDO, manual, con copias fechadas de listas, datos y estructura, sin sobrescribir anteriores. Sin base Access local de respaldo y sin adjuntos. Falta especificar recuperación y alcance técnico.

Nómina: No gestionar pagos en SENTINEL. El ETA determina el período para el reporte de barcos trabajados y cerrados. Registro separado de entrada/salida/amanecida con base propia es solo una posibilidad, no alcance aprobado.

Modularidad obligatoria: Pantallas, lógica, datos, permisos, historial, reportes y configuración separados. Contratos documentados para cambiar un módulo sin tocar todo el sistema.

Aclaración sobre respaldo: botón manual HACER RESPALDO. Cada ejecución conserva una copia fechada de las listas, sus datos y estructura/configuración recuperable. No sobrescribir las copias anteriores con modificaciones o eliminaciones maliciosas. No crear base local Access para este respaldo. No adjuntos, porque fueron excluidos del alcance. Falta acordar método, permisos, consistencia y alcance de recuperación; exportar solo Excel no prueba que pueda restaurarse la estructura.

Aclaración sobre privacidad: que los auditores desconozcan la URL no protege las listas. El diseño debe demostrar permisos reales sobre estructura, operaciones y evaluación, incluyendo acceso directo a SharePoint; no basta ocultar botones o pantallas. No prometer invulnerabilidad del historial.
